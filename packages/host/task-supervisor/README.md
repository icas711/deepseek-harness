# `@deepseek-ai/dsh-task-supervisor`

Долговечный супервизор задач для веб-поверхности: реестр задач в домашней папке, мягкий рестарт (парковка `running`-задач при остановке и автоматическое возобновление после старта) и явное управление жизненным циклом задачи через сервис `ctx.taskSupervisor`.

## Сервис `ctx.taskSupervisor`

| Метод | Контракт |
|---|---|
| `track({ sessionId, title, stationId? })` | Регистрирует работу на сессии. Идемпотентен по `sessionId`: повторный вызов с тем же заголовком и привязкой ничего не пишет, вызов с новым — перезаписывает заголовок; явный `stationId` перепривязывает запись, опущенный — сохраняет прежнюю привязку; у сессии с завершённой задачей открывается новая задача с новым `taskId`. Владение станцией проверяет вызывающая сторона (RPC-граница): сервис доверяет брендированному идентификатору. |
| `markCompleted(taskId)` | Переводит задачу в `completed` из `running`/`paused`/`interrupted`/`waiting-station`. |
| `markFailed(taskId, reason)` | Переводит задачу в `failed` (из тех же статусов); непустая причина фиксируется в логе процесса (формат записи в файле — фиксированный набор полей, причина в файл не пишется). |
| `list()` | Копии всех записей в порядке реестра. |
| `resume(taskId)` | Возобновляет `paused`/`interrupted`/`waiting-station` задачу: открывает сессию (живой агент переиспользуется, холодная — возобновляется из durable-хранилища с композицией записанного пресета и, для привязанных задач, с миром исполнения станции) и доставляет сообщение-продолжение; при неудаче запись возвращается к прежнему статусу. |

## Реестр и жизненный цикл

Документ `task-registry.json` (путь — обязательное поле конфига `registryPath`; композиция передаёт `dshHomePath('task-registry.json')`) хранит записи `{ taskId, sessionId, title, status, updatedAt, stationId? }`, где `taskId` — брендированный непрозрачный идентификатор, `status` — `running`/`paused`/`interrupted`/`waiting-station`/`completed`/`failed`, а необязательный `stationId` — брендированная привязка к станции исполнения. Поле опциональное, структурная версия документа не менялась: разбор принимает документ без `stationId` (задача в мире хоста), а при наличии поля требует непустую строку — мусор валит загрузку громко; старый читатель новый документ со статусом `waiting-station` отвергнет так же громко. Каждая мутация перерисовывает весь документ и коммитит его через writer-lock из `dsh-atomic-write` с ограниченным ретраем замены: читатели видят только целое старое или целое новое содержимое, второй процесс с общей домашней папкой сливается по `taskId`, а `EPERM` на переименовании в окне рестарта (сканер держит свежий файл) переживается бэкоффом и громко падает лишь по дедлайну. Битый документ роняет загрузку сервиса громко, с подсказкой оператору, — молча терять задачи нельзя.

При чистой выгрузке fiber'а супервизор сперва гасит незавершённые возобновления, затем одной атомарной записью переводит все `running`-задачи в `paused` и только потом разбирает поднятых им агентов — порядок disposals по defensive-patterns. При старте записи `running` означают жёсткий сбой предшественника: они одной записью помечаются `interrupted` и автоматически НЕ возобновляются (только явным `resume`); записи `paused` возобновляются сами, как только в композиции появляется фабрика агентов (`ctx.inject(['agentLoop'])`). Пустой реестр — пассивный режим: сессии не открываются, в логе тихо.

### Привязка к станции и статус `waiting-station`

Задача с `stationId` живёт в мире исполнения своей станции. Когда мост станций (`ctx.stations`, опциональная композиция) поднимает событие `station/status` с `online: false`, супервизор одной атомарной записью переводит все `running`-задачи этой станции в `waiting-station`; ход агента при этом не гасится — инструменты офлайн-станции отвечают понятными ошибками шва. Когда станция возвращается (`online: true`), каждая `waiting-station`-задача продолжается автоматически, по механике `paused`→`resume`: холодная сессия открывается заново (с переприменением мира станции — провайдеры fs-station/subprocess-station монтируются в скоуп агента с приватными isolate-метками), и доставляется обычное сообщение-продолжение со станционной формулировкой. Единственное исключение: если ход агента всё ещё в полёте (не гасился), сообщение-продолжение НЕ добавляется — задача продолжает текущий шаг сама, а лишний followup встал бы очередью за живым ходом. Возобновлённая задача требует мост станций в композиции: без `ctx.stations` возобновление привязанной задачи падает громко (`resume-unavailable`), а не уводит инструменты на локальную машину. Статус `waiting-station` переживает рестарт хоста (уход станции не отменён рестартом) и снимается только возвратом станции или явным завершением. Подписка на события регистрируется в `init` только при смонтированном мосте и гасится вместе с fiber'ом.

## Model Experience

### Continuation input after a supervisor restart

#### What the model sees

Каждое автоматическое или явное возобновление доставляет в сессию одно обычное пользовательское сообщение (обычный вход в лог, без новых типов событий) с константой ниже — тем же путём, что и ручной ввод, только с источником `plugin: @deepseek-ai/dsh-task-supervisor`.

##### Verbatim text for this field, when needed

```markdown
Задача была прервана рестартом сервера. Продолжи выполнение с места остановки; сначала кратко восстанови контекст по истории.
```

Для задачи, продолженной возвратом станции, вместо текста выше доставляется станционная константа:

```markdown
Связь со станцией восстановлена. Продолжи выполнение задачи с места остановки.
```

#### Token effect

Одно короткое сообщение (35 слов) на каждое возобновление задачи; условное — только после рестарта с приостановленными задачами, явного `resume` или возврата станции, к которой привязана ожидавшая задача (11 слов). Возобновление `waiting-station`-задачи с ходом в полёте сообщения не доставляет вовсе.

#### KV Cache effect

Обычный append в лог сессии: достраивает хвост истории и не переписывает прежние запросы; повторных возобновлений одной и той же задачи без рестарта не бывает, так что многократной вставки одного и того же текста нет.

## Known Limitations and Deferred Work

- **Нет модель-видимого управления задачами** — `track`/`markCompleted`/`markFailed`/`list`/`resume` пока доступны только как API сервиса; инструмента и RPC-эндпоинтов нет, поэтому в композиции по умолчанию их никто не вызывает, и автоматическое возобновление ожидает интеграцию владельца задач (этап 3).
- **Статус `waiting-human` не предусмотрен** — известное ограничение этапа; задачи, чей ход требует человека, остаются `running` и после рестарта возобновляются с тем же продолжением.
- **Авто-возобновление требует persistence и фабрику агентов** — без `dsh-session-persistence`-бэкенда или без agent-loop в композиции возобновление недоступно (`resume-unavailable`), `track`/`list`/завершения работают; `inject(['agentLoop'])` без смонтированного цикла просто не срабатывает.
- **Мир станции при возобновлении — по записи задачи** — холодное открытие переприменяет мир станции из `stationId` записи; сессия, созданная через `session.create` с `executionTarget`, но без привязанной задачи в реестре, после рестарта возобновляется шлюзом в локальном мире (привязку сессии к задаче делает интеграция владельца задач).
- **Смена мира видима скоупу, а не всему хосту** — провайдеры fs-station/subprocess-station монтируются в скоупе агента с приватными isolate-метками (механика preset/isolate): инструменты, смонтированные в том же скоупе, видят станцию, хостовые — локальный мир.
- **Возобновлённый агент не восстанавливает выбор модели сессии** — холодная открытая сессия получает дефолтную модель из `ctx.agentDefaultModel`; выбор конкретной сессии (как в API-шлюзе) не читается.
- **Реестр не чистится** — завершённые записи остаются в документе навсегда; ротации/лимита размера нет.
