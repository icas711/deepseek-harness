# `@deepseek-ai/dsh-telegram-notifier`

Telegram-провайдер возможности уведомлений ([`dsh-notifier`](../notifier/README.md)) и Consumer статусов задач в одном пакете. Доставка — обычный `sendMessage`, приём кодов сопряжения — периодический `getUpdates`: ни webhook’а, ни входящих портов. Бот отвечает на русском, тексты — константы пакета.

## Как это включается

Строка `telegram-notifier` бандл-патча монтирует плагин из `DSH_TELEGRAM_BOT_TOKEN` и `DSH_WEB_URL`:

- **Пустой или отсутствующий токен — пассивный режим**: сервис `ctx.notifier` не монтируется, таймеров и сетевых эффектов нет (то же правило, что у `web-auth`).
- **С токеном** строка монтирует провайдер: `ctx.notifier` начинает доставлять уведомления, бот периодически опрашивает `getUpdates`, а рядом с `ctx.taskSupervisor` стартует наблюдатель статусов задач.

Токен создаётся у @BotFather; боту ничего, кроме токена, не нужно — сообщения он получает опросом.

## Сопряжение

1. Пользователь запрашивает код (`ctx.notifier.beginBinding(login)` — страница привязки и RPC на следующем этапе); код живёт `bindingCodeTtlMs` (по умолчанию 15 минут) и одноразовый.
2. Пользователь отправляет боту сообщение вида `/start КОД`.
3. Провайдер достаёт код из `getUpdates`, сверяет с таблицей ожидающих и через `completeBinding` коммитит привязку «логин → chatId» в `telegram-bindings.json`; боту уходит подтверждение «Аккаунт «логин» привязан: …».
4. Чужой или истёкший код получает ответ «Код не найдён или истёк…», любое не-`/start` сообщение — подсказку.

`getUpdates` ходит с периодом `pollIntervalMs` (по умолчанию 3 с) в режиме короткого опроса (`timeout: 0`); обновление подтверждается смещением offset **до** обработки — «ядовитое» обновление не блокирует очередь, а несостоявшаяся привязка просто остаётся без ответа (пользователь запрашивает новый код). Сетевые сбои опроса пишутся в лог и не роняют процесс.

## Consumer: наблюдатель статусов задач

У `ctx.taskSupervisor` нет ленты событий, поэтому наблюдатель раз в `watchIntervalMs` (по умолчанию 15 с) читает `list()` и сравнивает статусы с предыдущим опросом в памяти. Уведомления уходят при переходе задачи в:

| Статус | Заголовок |
|---|---|
| `paused` | Требуется действие: задача приостановлена |
| `interrupted` | Требуется действие: задача прервана сбоем |
| `waiting-station` | Задача ждёт станцию |
| `completed` | Задача завершена |
| `failed` | Задача провалена |

Статус `running` — не новость, кроме одного перехода: `waiting-station` → `running` означает, что станция задачи вернулась и супервизор продолжил её автоматически — такой переход доставляет уведомление с заголовком «Станция вернулась — задача продолжена», один раз на переход; новое наблюдение `waiting-station` перезаряжает его. Переходы, случившиеся между двумя опросами (молниеносный офлайн-цикл короче `watchIntervalMs`), наблюдатель не видит — как и любой другой дифф-переход.

Уведомление адресуется всем логинам с подтверждённым биндингом (`boundLogins()`); в тексте — только название задачи, статус в заголовке и ссылка `DSH_WEB_URL` + `/session/` + `sessionId` (без `DSH_WEB_URL` ссылки нет). Дедупликация: одно активное уведомление на пару (задача, статус) — пара переоткрывается, только когда задача уходит из статуса; пара, чья доставка не удалась или у которой ещё нет биндинга, остаётся неотмеченной и повторяется на следующем опросе.

## Конфиг

| Поле | По умолчанию | Смысл |
|---|---|---|
| `botToken` | — (из `DSH_TELEGRAM_BOT_TOKEN`) | Токен бота; пустой — пассивный режим. |
| `webBaseUrl` | — (из `DSH_WEB_URL`) | База ссылок на сессии. |
| `bindingsPath` | `dshHomePath('telegram-bindings.json')` | Документ биндингов (владеет `dsh-notifier`). |
| `bindingCodeTtlMs` | 900 000 | Срок жизни кода сопряжения. |
| `pollIntervalMs` | 3 000 | Период `getUpdates` (минимум 50 мс). |
| `watchIntervalMs` | 15 000 | Период опроса задач (минимум 50 мс). |

## Model Experience

None, as `telegram` is notification plumbing: nothing it owns enters a model request, and its texts travel to a human’s Telegram chat, not to the model.

#### KV Cache effect

No direct effect: the package adds no prompt sections, no tools, and no logged input.

## Known Limitations and Deferred Work

- **UI-страница привязки и RPC — следующий этап** — коды пока выдаются только вызовом `ctx.notifier.beginBinding`; страницы «Уведомления» и RPC-эндпоинтов нет.
- **Уведомления уходят всем привязанным** — наблюдатель не знает, какому логину принадлежит сессия задачи: реестр задач не хранит логин. Когда владелец появится в реестре или через RPC, адресация станет персональной.
- **Отвязки нет, смена чата — только через повторное сопряжение** — повторный `/start КОД` перезаписывает `chatId` логина; отвязать логин нельзя (ограничение документа биндингов).
- **Сообщения боту до старта процесса** — `getUpdates` с offset 0 заберёт непрочитанные обновления за последние сутки; более старые Telegram уже не отдаёт, и код из такого сообщения не сработает.
