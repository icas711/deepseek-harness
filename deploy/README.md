# Развёртывание DeepSeek Harness на арендованном сервере (Docker)

Инструкция поднимает веб-GUI (`dsh web`) в контейнере на удалённом сервере. С любого компьютера открываете GUI в браузере — и работаете с одним и тем же агентом, одним рабочим пространством и одним набором сессий.

```
компьютер 1 ─┐
компьютер 2 ─┼─ браузер ──HTTPS──▶ Caddy ──▶ контейнер dsh web ──▶ том dsh-home (сессии)
компьютер 3 ─┘                                    │
                                                  └──▶ ./workspace (файлы проектов)
```

Почему сессии синхронизируются сами: сервер один, все сессии хранятся на нём в томе `dsh-home` (`$DSH_HOME/storages`), а браузеры — тонкие клиенты. Нет никакой отдельной «синхронизации»: список сессий, история и настройки общие, потому что физически существуют в одном месте. Параллельно открытые с нескольких машин вкладки видят одно и то же; работать в одной и той же сессии одновременно с двух машин технически возможно, но осмысленно — по очереди: агент исполняет одну цепочку действий за раз.

## 0. Что понадобится

- VPS: Ubuntu 22.04/24.04, 2 vCPU, **4 GB RAM** (сборка образа — tsc + vite, на 2 GB может не влезть: см. «Если мало RAM»), 20+ GB диска.
- Docker Engine с compose-плагином (ставится скриптом ниже).
- Для варианта с HTTPS — домен, чья A-запись указывает на сервер. Без домена тоже можно: SSH-туннель или прямой доступ по IP (см. «Доступ с компьютеров»).

## 1. Подготовка сервера

```bash
ssh root@SERVER_IP

# Docker Engine + compose-плагин
curl -fsSL https://get.docker.com | sh

# Файрвол: SSH и порты веба. Порт 3080 наружу НЕ открываем —
# к нему пускаем только через туннель или Caddy.
ufw allow OpenSSH
ufw allow 80,443/tcp
ufw enable
```

Если выбираете «прямой доступ по IP» без домена, дополнительно `ufw allow 3080/tcp`. Помните: это будет чистый HTTP, токен ходит по сети открытым текстом — годится для частной сети/VPN, не для постоянной работы из интернета.

## 2. Код на сервере

```bash
mkdir -p /opt/dsh && cd /opt/dsh
git clone <URL вашего форка> deepseek-harness
cd deepseek-harness
```

Для приватного репозитория добавьте на сервер deploy key с правом чтения.

## 3. Конфигурация

```bash
cd deploy
cp .env.example .env
chmod 600 .env
openssl rand -hex 24          # результат — в DSH_WEB_TOKEN
nano .env
```

Заполните три переменных в `deploy/.env`:

- `DEEPSEEK_API_KEY` — ключ модели;
- `DSH_WEB_TOKEN` — токен входа в GUI (сгенерирован выше). Обязателен: compose не поднимет стек без него, потому что без токена доступом к GUI фактически становится любой, кто достучался до порта, а GUI управляет агентом, исполняющим команды на сервере;
- `DSH_PUBLIC_HOST` — адрес из строки браузера: домен (рекомендуется) или IP. Он попадает в `--trusted-host` — это список внешних адресов, которые принимает анти-DNS-rebinding fence сервера. Адрес в браузере должен совпадать с ним, иначе `/api` отвечает 403.

Для HTTPS отредактируйте `deploy/Caddyfile` — замените `dsh.example.com` на свой домен. Caddy сам получит и продлит сертификат Let's Encrypt.

## 4. Запуск

Вариант с доменом и HTTPS (рекомендуется):

```bash
docker compose --profile tls up -d --build
docker compose logs -f dsh
```

Без домена (только SSH-туннель):

```bash
docker compose up -d --build
```

Первая сборка занимает несколько минут (pnpm install + tsc + vite). Дождитесь в логах строки вида `dsh web: http://127.0.0.1:3080` — сервер поднялся. Профиль `web` инициализируется сам при первом старте и живёт в томе `dsh-home`, его не нужно создавать вручную.

Рабочая папка агента — `deploy/workspace` (bind mount в `/workspace` контейнера): все файлы, которые создаёт агент, лежат на хосте в обычном каталоге и переживают что угодно. При желании положите туда проект до первого запуска.

## 5. Доступ с компьютеров

Любой компьютер: открыть адрес и один раз предъявить токен — сервер поставит cookie `dsh_web_token`, дальше браузер входит сам.

- **Через домен:** `https://<домен>/?token=<DSH_WEB_TOKEN>`
- **Через SSH-туннель** (без домена): `ssh -L 3080:127.0.0.1:3080 root@SERVER_IP`, затем на своём компьютере `http://127.0.0.1:3080/?token=<DSH_WEB_TOKEN>`. Loopback проходит fence без `--trusted-host`.
- **Прямо по IP** (HTTP, только для частной сети/VPN): в `deploy/.env` укажите `DSH_PUBLIC_HOST=<IP сервера>`, откройте порт (`ufw allow 3080/tcp`), затем `http://<IP>:3080/?token=<DSH_WEB_TOKEN>`.

Новый токен после смены: обновите `DSH_WEB_TOKEN` в `deploy/.env` и выполните `docker compose up -d` (cookie старого токена перестанут принимать, у всех компьютеров потребуется один вход по `?token=`).

## Обновление кода

Контейнер одноразовый по построению: код живёт в образе, пользовательский стейт — в томе `dsh-home` (сессии, профиль, credentials) и в `deploy/workspace` (файлы). Обновление = пересобрать образ и пересоздать контейнер.

```bash
cd /opt/dsh/deepseek-harness

# 1) Бэкап сессий — перед КАЖДЫМ обновлением (см. раздел ниже и почему).

# 2) Обновить код и пересобрать
git pull --ff-only          # лучше: git checkout <тег или коммит>
docker compose build        # + --profile tls, если он у вас включён
docker compose up -d

# 3) Проверить
docker compose logs -f dsh  # строка `dsh web: ...` — сервер поднялся
```

Затем откройте GUI и убедитесь, что список сессий на месте и новая сессия отвечает.

Почему бэкап обязателен и почему стоит обновляться на тег/коммит, а не на `master`: проект до релиза, и для формата сессий на диске совместимости не обещают — новая версия может отказаться читать логи, записанные старой, а откат старой версией на «будущие» сессии тем более не гарантирован. Пинковаться на конкретный тег/коммит и обновляться осознанно — это страховка от потери истории посреди работы. Откат: `git checkout <предыдущий тег>`, `docker compose build && docker compose up -d`, при необходимости — восстановление из бэкапа.

Что при обновлении теряется, а что нет:

- остаётся: сессии и профиль (`dsh-home`), файлы проектов (`deploy/workspace`), настройки и credentials (`dsh-home`);
- пересобирается с нуля: код, `node_modules`, фронтенд (внутри образа);
- сбрасывается: незавершённые запуски агента — фоновые задачи и незакрытые ходы модели не доживают до пересоздания контейнера, дождитесь их окончания перед `up -d`.

## Бэкап и восстановление

```bash
cd /opt/dsh/deepseek-harness/deploy

# Сессии, профиль, credentials — из тома:
docker compose exec -T dsh tar czf - -C /data dsh-home > "dsh-home-$(date +%F).tgz"

# Восстановление (стек лучше остановить: docker compose stop dsh):
docker compose exec -T dsh tar xzf - -C /data < dsh-home-2025-01-01.tgz
```

Файлы проектов лежат прямо в `deploy/workspace` — бэкапьте как обычный каталог (`tar czf workspace-....tgz workspace/`). Храните архивы вне сервера (rsync/scp на другую машину) — бэкап на том же диске защищает только от форматов, не от диска.

## Если мало RAM

Сборка (tsc + tsdown + vite) на VPS с 2 GB может падать по OOM. Два пути:

- Добавить swap: `fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile && echo '/swapfile none swap sw 0 0' >> /etc/fstab` и пересобрать.
- Собрать образ на своём компьютере и перевезти: локально `docker build -f deploy/Dockerfile -t dsh-web:local .`, затем `docker save dsh-web:local | ssh root@SERVER_IP 'docker load'`, на сервере сразу `docker compose up -d` (compose увидит готовый `image: dsh-web:local` и не будет пересобирать). Рантайму хватает 1–2 GB.

## Диагностика

- **401 в браузере** — токен не предъявлен или неверный: откройте адрес с `?token=<DSH_WEB_TOKEN>`; после правки токена не забудьте `docker compose up -d`.
- **403 на `/api`, страница при этом открывается** — анти-rebinding fence не знает адрес из строки браузера: `DSH_PUBLIC_HOST` в `deploy/.env` должен в точности совпадать с хостом, который вы вводите (для доступа по другому адресу добавьте его ещё одной парой строк `--trusted-host` в `deploy/compose.yaml` и перезапустите `docker compose up -d`).
- **Агент не отвечает, в логах ошибка LLM** — проверьте, что `DEEPSEEK_API_KEY` задан в `deploy/.env`, и пересоздайте контейнер (`docker compose up -d`).
- **Посмотреть итоговую конфигурацию без запуска сервера:** `docker compose run --rm dsh web --dump-config` — печатает собранное дерево плагинов с указанием, какой слой задал каждую строку.
- **Логи:** `docker compose logs -f dsh` (ротация настроена: 3 × 10 MB).

## Безопасность: что важно понимать

`DSH_WEB_TOKEN` — это доступ к серверу: GUI управляет агентом, который исполняет команды и пишет файлы. Поэтому: токен длинный и случайный; порт 3080 не публикуется наружу; HTTPS через Caddy или SSH-туннель вместо чистого HTTP; ключи API — только в `deploy/.env` с правами 600; обновления безопасности контейнера — периодический `docker compose build --no-cache && docker compose up -d`. Внутри контейнера песочницей служит сам контейнер (плюс Landlock-лаунчер, собираемый в образе, для изоляции команд агента).
