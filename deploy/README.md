# Развёртывание DeepSeek Harness на арендованном сервере (Docker)

Инструкция поднимает веб-GUI (`dsh web`) в контейнере на удалённом сервере. Вход — по логину и паролю: каждый пользователь получает собственный «кабинет» (папку в workspace и свои сессии), выделенные админы видят всё. С любого компьютера открываете GUI в браузере — и работаете со своими сессиями и своими файлами.

```
компьютер 1 ─┐
компьютер 2 ─┼─ браузер ──HTTPS──▶ Caddy ──▶ контейнер dsh web ──▶ том dsh-home (сессии)
компьютер 3 ─┘                                    │
                                                  └──▶ ./workspace/<логин> (кабинеты пользователей)
```

Почему сессии синхронизируются сами: сервер один, все сессии хранятся на нём в томе `dsh-home` (`$DSH_HOME/storages`), а браузеры — тонкие клиенты. Нет никакой отдельной «синхронизации»: список сессий, история и настройки живут в одном месте. Параллельно открытые вкладки одного пользователя видят одно и то же; работать в одной и той же сессии одновременно с двух машин технически возможно, но осмысленно — по очереди: агент исполняет одну цепочку действий за раз. Один логин — одна активная сессия входа: новый вход (с другого компьютера или после «Выйти») сразу завершает предыдущую.

## 0. Что понадобится

- VPS: Ubuntu 22.04/24.04, 2 vCPU, **4 GB RAM** (сборка образа — tsc + vite, на 2 GB может не влезть: см. «Если мало RAM»), 20+ GB диска.
- Docker Engine с compose-плагином (ставится скриптом ниже).
- Node.js 22+ на машине, где готовите `deploy/.env` — для генерации хэшей паролей (подойдёт ноутбук, сервер не нужен).
- Для варианта с HTTPS — домен, чья A-запись указывает на сервер. Без домена тоже можно: SSH-туннель или прямой доступ по IP (см. «Доступ с компьютеров»).

## 1. Подготовка сервера

```bash
ssh root@SERVER_IP

# Docker Engine + compose-плагин
curl -fsSL https://get.docker.com | sh

# Файрвол: SSH и порты веба. Порт 3080 наружу НЕ открываем —
# к нему пускаем только через туннель или Caddy.
ufw allow OpenSSH
ufw allow 80,443/tcp
ufw enable
```

Если выбираете «прямой доступ по IP» без домена, дополнительно `ufw allow 3080/tcp`. Помните: это будет чистый HTTP, пароль ходит по сети открытым текстом — годится для частной сети/VPN, не для постоянной работы из интернета.

## 2. Код на сервере

```bash
mkdir -p /opt/dsh && cd /opt/dsh
git clone <URL вашего форка> deepseek-harness
cd deepseek-harness
```

Для приватного репозитория добавьте на сервер deploy key с правом чтения.

## 3. Конфигурация

```bash
cd deploy
cp .env.example .env
chmod 600 .env
node hash-password.mjs alice      # пароль спросит скрипт; готовую строку вставьте в .env
nano .env
```

Заполните переменные в `deploy/.env`:

- `DEEPSEEK_API_KEY` — ключ модели;
- `DSH_WEB_USERS` — пользователи GUI: записи `логин:scrypt-хэш` через запятую. Хэш генерирует `node hash-password.mjs <логин>` — его готовую строку `DSH_WEB_USERS='...'` вставьте в `.env` целиком. **Одинарные кавычки обязательны**: compose разворачивает `$` в значениях `.env` и без кавычек молча портит scrypt-хэш (вида `scrypt$16384$8$1$salt$key`), принимая `$16384` и `$8` за переменные. Обязателен: compose не поднимет стек без него, потому что GUI управляет агентом, исполняющим команды на сервере, а без списка логинов доступом к GUI фактически становится любой, кто достучался до порта;
- `DSH_WEB_ADMINS` — необязательно: логины-админы через запятую, видят сессии и папки всех пользователей (логин должен быть и в `DSH_WEB_USERS`);
- `DSH_PUBLIC_HOST` — адрес из строки браузера: домен (рекомендуется) или IP. Он попадает в `--trusted-host` — это список внешних адресов, которые принимает анти-DNS-rebinding fence сервера. Адрес в браузере должен совпадать с ним, иначе `/api` отвечает 403.

Каждый логин из `DSH_WEB_USERS` — отдельный кабинет: при первом входе сервер создаёт `/workspace/<логин>`, и пользователь видит только свои сессии и свою папку. Смена пароля (новый хэш в `DSH_WEB_USERS` + `docker compose up -d`) немедленно отзывает сессии этого логина; удаление логина отзывает их навсегда.

Для HTTPS домен нужен только в `DSH_PUBLIC_HOST` (`deploy/.env`): из неё он попадает и в `--trusted-host`, и в Caddyfile (`{$DSH_PUBLIC_HOST}`). Caddy сам получит и продлит сертификат Let's Encrypt; для выдачи сертификата нужен именно домен — для IP-адреса Let's Encrypt сертификат не выдаёт.

## 4. Запуск

Вариант с доменом и HTTPS (рекомендуется):

```bash
docker compose --profile tls up -d --build
docker compose logs -f dsh
```

Без домена (только SSH-туннель):

```bash
docker compose up -d --build
```

Первая сборка занимает несколько минут (pnpm install + tsc + vite). Дождитесь в логах строки вида `dsh web: http://127.0.0.1:3080` — сервер поднялся. Профиль `web` инициализируется сам при первом старте и живёт в томе `dsh-home`, его не нужно создавать вручную.

> **Перезапуск прерывает активные задачи.** `docker compose up -d` после правки `.env` и обновление пересоздают контейнер: незакрытый ход модели и фоновые команды агента не доживают до нового контейнера. `stop_grace_period: 130s` даёт серверу две минуты на аккуратное завершение текущего шага, потом Docker посылает SIGKILL, — дождитесь окончания активных сессий перед перезапуском.

Рабочая папка агента — `deploy/workspace` (bind mount в `/workspace` контейнера): все файлы, которые создаёт агент, лежат на хосте в обычном каталоге и переживают что угодно. Внутри неё у каждого логина свой кабинет `/workspace/<логин>` — он создаётся при первом входе; при желании положите в кабинет проект до первого запуска.

## 5. Доступ с компьютеров

Любой компьютер: открыть адрес — сервер покажет страницу входа. Введите логин и пароль из `DSH_WEB_USERS`; сервер поставит cookie сессии (30 дней, переживает рестарт контейнера), дальше браузер входит сам. «Выйти» — кнопка внизу боковой панели.

- **Через домен:** `https://<домен>/`
- **Через SSH-туннель** (без домена): `ssh -L 3080:127.0.0.1:3080 root@SERVER_IP`, затем на своём компьютере `http://127.0.0.1:3080/`. Loopback проходит fence без `--trusted-host`.
- **Прямо по IP** (HTTP, только для частной сети/VPN): в `deploy/.env` укажите `DSH_PUBLIC_HOST=<IP сервера>`, откройте порт (`ufw allow 3080/tcp`), затем `http://<IP>:3080/`.

Управление пользователями — правка `DSH_WEB_USERS` в `deploy/.env` и `docker compose up -d`:

- **Сменить пароль:** новый хэш (`node hash-password.mjs <логин>`) вместо старого. Сессии этого логина отзовутся немедленно — потребуется один новый вход; остальные пользователи не заметят перезапуска.
- **Добавить пользователя:** дописать `логин:хэш` через запятую. Кабинет создастся при первом входе.
- **Удалить пользователя:** убрать запись. Его сессии отзовутся; кабинет `/workspace/<логин>` остаётся на диске (доступ получат только админы и root сервера).
- **Назначить админа:** дописать логин в `DSH_WEB_ADMINS`. Админ видит сессии и папки всех; сессии, созданные до включения входа по паролю (cwd в корне workspace), тоже видны только админам.

Неинтерактивный доступ (curl) — HTTP Basic тем же логином и паролем: `curl -u alice:пароль https://<домен>/api/...`. После 5 неудачных попыток входа подряд с одного адреса сервер держит минутную паузу (429).

## Обновление кода

Контейнер одноразовый по построению: код живёт в образе, пользовательский стейт — в томе `dsh-home` (сессии, профиль, credentials) и в `deploy/workspace` (файлы). Обновление = пересобрать образ и пересоздать контейнер.

```bash
cd /opt/dsh/deepseek-harness

# 1) Бэкап сессий — перед КАЖДЫМ обновлением (см. раздел ниже и почему).

# 2) Обновить код и пересобрать
git pull --ff-only          # лучше: git checkout <тег или коммит>
docker compose build        # + --profile tls, если он у вас включён
docker compose up -d

# 3) Проверить
docker compose logs -f dsh  # строка `dsh web: ...` — сервер поднялся
```

Затем откройте GUI и убедитесь, что список сессий на месте и новая сессия отвечает.

Почему бэкап обязателен и почему стоит обновляться на тег/коммит, а не на `master`: проект до релиза, и для формата сессий на диске совместимости не обещают — новая версия может отказаться читать логи, записанные старой, а откат старой версией на «будущие» сессии тем более не гарантирован. Пинковаться на конкретный тег/коммит и обновляться осознанно — это страховка от потери истории посреди работы. Откат: `git checkout <предыдущий тег>`, `docker compose build && docker compose up -d`, при необходимости — восстановление из бэкапа.

Что при обновлении теряется, а что нет:

- остаётся: сессии и профиль (`dsh-home`), файлы проектов (`deploy/workspace`), настройки и credentials (`dsh-home`);
- пересобирается с нуля: код, `node_modules`, фронтенд (внутри образа);
- сбрасывается: незавершённые запуски агента — фоновые задачи и незакрытые ходы модели не доживают до пересоздания контейнера, дождитесь их окончания перед `up -d`.

## Бэкап и восстановление

```bash
cd /opt/dsh/deepseek-harness/deploy

# Сессии, профиль, credentials — из тома:
docker compose exec -T dsh tar czf - -C /data dsh-home > "dsh-home-$(date +%F).tgz"

# Восстановление (стек лучше остановить: docker compose stop dsh):
docker compose exec -T dsh tar xzf - -C /data < dsh-home-2025-01-01.tgz
```

Файлы проектов лежат прямо в `deploy/workspace` — бэкапьте как обычный каталог (`tar czf workspace-....tgz workspace/`). Храните архивы вне сервера (rsync/scp на другую машину) — бэкап на том же диске защищает только от форматов, не от диска.

## Если мало RAM

Сборка (tsc + tsdown + vite) на VPS с 2 GB может падать по OOM. Два пути:

- Добавить swap: `fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile && echo '/swapfile none swap sw 0 0' >> /etc/fstab` и пересобрать.
- Собрать образ на своём компьютере и перевезти: локально `docker build -f deploy/Dockerfile -t dsh-web:local .`, затем `docker save dsh-web:local | ssh root@SERVER_IP 'docker load'`, на сервере сразу `docker compose up -d` (compose увидит готовый `image: dsh-web:local` и не будет пересобирать). Рантайму хватает 1–2 GB.

## Диагностика

- **Контейнер перезапускается или в `docker compose ps` горит `unhealthy`** — смотрите `docker compose logs dsh`: healthcheck опрашивает страницу `/login`, и его провал значит, что сервер не поднялся (обычно в логах видна ошибка загрузки конфигурации).
- **Страница входа не пускает** — неверный логин или пароль (страница так и напишет), либо сессия кончилась после смены пароля — войдите заново. После 5 неудач подряд с одного адреса сервер минуту отвечает паузой — это защита от подбора, не поломка.
- **Вход проходит, но 401 на `/api`** — сессия истекла (30 дней) или вход выполнили с другого компьютера под тем же логином: перезагрузите страницу и войдите снова.
- **403 на `/api`, страница при этом открывается** — анти-rebinding fence не знает адрес из строки браузера: `DSH_PUBLIC_HOST` в `deploy/.env` должен в точности совпадать с хостом, который вы вводите (для доступа по другому адресу добавьте его ещё одной парой строк `--trusted-host` в `deploy/compose.yaml` и перезапустите `docker compose up -d`).
- **Агент не отвечает, в логах ошибка LLM** — проверьте, что `DEEPSEEK_API_KEY` задан в `deploy/.env`, и пересоздайте контейнер (`docker compose up -d`).
- **Посмотреть итоговую конфигурацию без запуска сервера:** `docker compose run --rm dsh web --dump-config` — печатает собранное дерево плагинов с указанием, какой слой задал каждую строку.
- **Логи:** `docker compose logs -f dsh` (ротация настроена: 3 × 10 MB).

## Известный пробел: bind-адрес задаётся патчем, а не переменной

По умолчанию веб-сервер слушает `127.0.0.1` (строка `webserver` патча бандла web-app), а флаг `--host 0.0.0.0` CLI отвергает (`packages/bundle/web-app/src/startup.ts:158`), поэтому бинд на все интерфейсы контейнера закрывается патч-оверлеем `deploy/web-remote.patch.yml`, который compose передаёт через `web --patch ...`. Механика патчей (`vendor/include/src/index.ts:121`) перезаписывает только перечисленные в патче поля: `config` строки заменяется целиком (поэтому в патче переписаны и `host`, и `port`), а `name` и `inject` строки сохраняются — `name` в патче служит стражем несовпадения.

Это рабочее, но громоздкое решение. Правильнее задавать хост из окружения: будущая переменная `DSH_WEB_HOST`, которую провайдер `web-startup` читал бы так же, как сейчас читает флаг `--host`, убрала бы из комплекта развёртывания и патч, и связанный с ним особый случай. Пока переменной нет, удалённый бинд держится на патче.

## Безопасность: что важно понимать

Учётная запись из `DSH_WEB_USERS` — это доступ к серверу: GUI управляет агентом, который исполняет команды и пишет файлы. Поэтому: пароли длинные и уникальные (хэши — scrypt); порт 3080 не публикуется наружу; HTTPS через Caddy или SSH-туннель вместо чистого HTTP; `deploy/.env` с хэшами и ключами API — права 600; обновления безопасности контейнера — периодический `docker compose build --no-cache && docker compose up -d`. Внутри контейнера песочницей служит сам контейнер (плюс Landlock-лаунчер, собираемый в образе, для изоляции команд агента).

Изоляция кабинетов честна против «любопытного соседа», а не против злого пользователя: сервер прячет чужие сессии и папки из списков, поиска и диалогов, но агент в своём кабинете исполняет команды в том же контейнере, что и агенты соседей — доверяйте тем, кого пускаете. Админ видит все сессии всех пользователей.
