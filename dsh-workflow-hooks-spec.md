# Spec: Workflow + Hooks для форка deepseek-harness

**Статус:** черновик / RFC
**Репозиторий:** форк `deepseek-ai/deepseek-harness`
**Мотивация:** перенести в dsh два примитива, которые в Claude Code (с v2.1.154, май 2026) заменили расчёт на текстовые инструкции в CLAUDE.md — Dynamic Workflows (скриптовая мультиагентная оркестрация) и Hooks (детерминированное принуждение правил на границах жизненного цикла агента).

---

## 0. На что опираемся в существующей архитектуре dsh

Прежде чем проектировать новое — то, что уже даёт Cordis (ядро dsh) практически бесплатно:

| Нужно нам | Уже есть в dsh |
|---|---|
| Точки перехвата тул-коллов | `tools/pre-execute` → permission/policy → `tools/execute` → `tools/post-execute` — уже симметрично Claude Code `PreToolUse`/`PostToolUse` |
| Короткое замыкание обработчика ("заблокировать") | Cordis waterfall dispatch — обработчик события может остановить цепочку, возвращая значение; ровно то же самое, что exit-code-2 в hook'ах Claude Code |
| Точка "агент решил, что закончил" | `agent/*` события: `inbox`, `step`, `status`, `request`, `validation`, `continuation` — `continuation` это наш аналог `Stop` |
| Изоляция запуска воркфлоу | Cordis fork/child context + автоматический dispose эффектов при unmount — не нужно городить свою песочницу |
| Персистентность/реплей | `session/event` — durable-факты, переживают reload; на них уже держится сессионный лог |
| Программируемая композиция без форка ядра | "Everything is a plugin" — оба компонента реализуются как обычные Cordis-плагины, монтируемые через `cordis.yml` |

Вывод: оба примитива **не требуют патчить ядро** — это два новых плагина, каждый claim'ит свой `ctx.<key>` и подписывается на уже существующие события. Это ровно тот путь, который архитектура dsh и предполагает.

**Перед тем как писать код:** проверить `awesome-deepseek-harness` (категория "core orchestration", 110+ плагинов) — не факт, что hook-подобного или workflow-подобного плагина там ещё нет. Дублировать экосистему смысла нет.

## 1. `dsh-plugin-hooks`

### 1.1 Цель
Детерминированное исполнение правил на границах событий, не зависящее от того, что "решила" модель. Хук — не просьба агенту, а код, который гарантированно выполняется.

### 1.2 Сервис и конфиг

Плагин не claim'ит новый `ctx.<key>` для чтения (только `ctx.hooks` для интроспекции/тестов), его основная работа — подписка на существующие события. Конфигурация — отдельный `hooks.yml`, монтируемый как обычный Cordis bundle:

```yaml
# hooks.yml
hooks:
  - event: tools/pre-execute
    match:
      tool: "fs.write|fs.edit"
      path: "**/.env*"
    run: scripts/block-env-edits.sh
    mode: block          # block | observe | rewrite

  - event: tools/post-execute
    match:
      tool: "fs.write|fs.edit"
      path: "**/*.go"
    run: scripts/gofmt-and-check.sh
    mode: rewrite

  - event: agent/continuation
    run: scripts/stop-guard.sh
    mode: block
```

### 1.3 Контракт исполнения (сохраняем формат, знакомый по Claude Code — переносить существующие скрипты почти 1:1)

- Хук получает JSON события на stdin: `{ event, tool?, input?, sessionId, turnId, stepId, ...payload }`.
- Exit code `0` → пропустить дальше по waterfall.
- Exit code `2` + текст в stderr → короткое замыкание waterfall (`mode: block`): событие не проходит дальше, текст ошибки уходит агенту как содержимое failed tool result — агент видит его на следующем шаге и может исправиться сам.
- Для `mode: rewrite` — хук пишет в stdout JSON `{ "output": "<новый payload>" }`, плагин подменяет им поле результата перед тем, как `tools/post-execute` дозаписывает durable tool result.
- Timeout на хук обязателен (конфигурируемый, дефолт 30с) — иначе повисший скрипт подвесит весь `step`.

### 1.4 Примеры (адаптация из Claude Code)

**Блокировка правки `.env`, что бы агент ни придумал:**
```bash
#!/usr/bin/env bash
input=$(cat)
path=$(echo "$input" | jq -r '.input.path // empty')
if [[ "$path" == *.env* ]]; then
  echo "Правка .env запрещена политикой репозитория." >&2
  exit 2
fi
exit 0
```

**Анти-петля на `agent/continuation` (аналог `stop_hook_active`):**
```bash
#!/usr/bin/env bash
input=$(cat)
if [ "$(echo "$input" | jq -r '.continuationRetry')" = "true" ]; then
  exit 0   # уже повторная проверка — не блокируем второй раз
fi
if ! pnpm test >/dev/null 2>&1; then
  echo "Тесты падают — почини перед завершением." >&2
  exit 2
fi
exit 0
```
Нужно завести поле `continuationRetry` в payload `agent/continuation` (или эквивалент), если его сейчас нет — иначе гарантированно получим бесконечный цикл при первом же блокирующем хуке.

### 1.5 Риски
- `tools/pre-execute`/`tools/post-execute` — общие события на все тулы; матчинг по имени тула + пути (glob) должен резолвиться до всех вложенных сабагентов, иначе хук молча не сработает внутри workflow-скрипта (см. §2).
- Хук-команды исполняются с правами пользователя, запустившего dsh — как и в Claude Code, это не sandbox, а doverennaya автоматизация; так и документировать.
- Порядок хуков на одном событии должен быть детерминирован (порядок объявления в `hooks.yml`), иначе непредсказуемо, чей `block` сработает первым.

## 2. `dsh-plugin-workflow`

### 2.1 Цель
Перенести оркестрацию из "текст в системном промпте → надежда, что модель вспомнит" в скрипт, который исполняется отдельно от интерактивной сессии, с параллелизмом и без раздувания контекста основного чата.

### 2.2 Новый сервис `ctx.workflow`

```ts
interface WorkflowService {
  run(script: string | WorkflowModule, input?: unknown): Promise<WorkflowRun>
  list(): WorkflowRunSummary[]          // для команды /workflows
  promote(runId: string, name: string): void  // сохранить как переиспользуемый тул
}
```

Реализуется как обычный Cordis-плагин с `inject: ['agents', 'sessions', 'tools', 'llm']` — он ничего не импортирует напрямую, только требует эти сервисы по имени, как и предписывает Cordis-примитив.

### 2.3 Формат скрипта воркфлоу

```ts
// workflows/audit-routes.ts
export const meta = {
  name: 'audit-routes',
  description: 'Аудит route-handler-ов на отсутствие auth-проверок',
}

export default async function ({ agent, pipeline }: WorkflowApi) {
  const found = await agent('Найди все .ts файлы в src/routes/.', {
    schema: { type: 'object', required: ['files'], properties: {
      files: { type: 'array', items: { type: 'string' } },
    }},
  })

  return pipeline(found.files, file =>
    agent(`Проверь ${file} на отсутствие auth-проверок.`, { label: file }),
  )
}
```

`WorkflowApi`:
- `agent(prompt, opts)` — поднимает дочернюю агент-сессию через `ctx.agents.spawn()`, ждёт финальное сообщение, валидирует по `opts.schema` (переиспользуем уже имеющуюся в Cordis-плагинах поддержку Standard Schema — не изобретаем свою валидацию).
- `pipeline(items, fn, opts?)` — fan-out с ограничением параллелизма (`opts.concurrency`, дефолт — например 8), fan-in результатов в массив.
- `tool(name, args)` — прямой вызов зарегистрированного тула в контексте воркфлоу, без агента, когда LLM не нужен (детерминированный шаг).

### 2.4 Модель исполнения — переиспользуем Cordis fork

Каждый `workflow.run()` открывает **child context через Cordis fork**, а не отдельный процесс/VM:
- Автоматический dispose всех эффектов (открытых сессий, таймеров) при завершении воркфлоу — бесплатно от Cordis, не пишем свою очистку.
- Каждый `agent()`-вызов внутри воркфлоу — это дочерняя `session`, живущая в изоляции от основной интерактивной сессии; в основной чат попадает только то, что воркфлоу explicitly вернул как результат (то же ограничение, что и у обычных Claude Code сабагентов — промежуточное не протекает наверх).
- Хуки из §1, повешенные на `tools/pre-execute`/`agent/continuation`, обязаны срабатывать и внутри дочерних сессий воркфлоу — они висят на событии, а не на конкретной сессии, так что это должно работать "из коробки", но это первое, что нужно покрыть e2e-тестом.

### 2.5 Персистентность и replay

Каждый шаг воркфлоу пишет `session/event` (durable) с типом `workflow/step` — payload включает имя шага, вход, результат, длительность. `ctx.workflow.list()` читает эти события для `/workflows`, ничего дополнительного хранить не нужно — session log уже это гарантирует.

### 2.6 Триггер запуска

Плагин подписывается на `agent/inbox` и проверяет префикс пользовательского сообщения (конфигурируемый маркер, дефолт `workflow:`), либо явную команду `/workflow <script>`. Более "жадный" режим по аналогии с `/effort ultracode` — конфигурируемый флаг профиля, при котором dsh для каждой существенной задачи сначала пытается построить workflow-скрипт вместо обычного пошагового агентского цикла; включать по умолчанию не стоит — дороже по токенам и времени, сначала обкатать на явном триггере.

### 2.7 Promotion в тул
`ctx.workflow.promote(runId, name)` регистрирует сохранённый скрипт как обычную запись в `ctx.tools` — раз "everything is a plugin", удачный воркфлоу становится первоклассным тулом без отдельного механизма "сохранённых команд".

## 3. Как компоненты дополняют друг друга здесь же, в dsh-терминах

- `dsh-plugin-workflow` даёт гибкость и параллелизм, но это по-прежнему LLM внутри `agent()` — она может интерпретировать задачу не так.
- `dsh-plugin-hooks` даёт гарантию на границах `tools/*` и `agent/continuation`, не зависящую от того, какой путь оркестрации сейчас исполняется — обычный чат, сабагент или дочерняя сессия воркфлоу.
- Прямое следствие §2.4: раз воркфлоу — это просто ещё один Cordis-контекст, хуки автоматически покрывают и его, не требуя отдельной интеграции. Это главное архитектурное преимущество переноса именно в dsh, а не повторной сборки с нуля.

## 4. Открытые вопросы

1. Есть ли в payload `agent/continuation` уже поле-аналог `stop_hook_active` — или его придётся добавлять патчем в `@deepseek-ai/agent`-пакет (тогда это уже не "просто плагин сбоку", а апстрим-патч)?
2. Гарантирует ли текущий waterfall dispatch синхронный порядок при параллельных `tools/pre-execute` из разных сабагентов workflow — или там свои гонки, которые обнаружатся только под нагрузкой?
3. dsh — developer preview, "THERE WILL BE COMPATIBILITY-BREAKING CHANGES" — стоит зафиксировать версию форка, от которой отсчитываем совместимость, и не гнаться за апстримом до стабилизации обоих плагинов.
4. Нужно свериться со списком в `awesome-deepseek-harness` / `dsh-external/hub` — возможно, часть §2 уже закрыта существующим orchestration-плагином, и имеет смысл форкнуть его, а не писать с нуля.

## 5. Черновой план внедрения

1. `dsh-plugin-hooks` на `tools/pre-execute`/`tools/post-execute` (самое изолированное, наименьший риск, максимальная немедленная польза — можно катить в свой `cordis.patch.yml` уже сейчас).
2. Добавить `agent/continuation`-хук + завести anti-loop поле, если его нет.
3. `dsh-plugin-workflow` с минимальным API (`agent`, `pipeline`) без promotion и без auto-режима.
4. E2E: хуки внутри дочерних сессий воркфлоу.
5. `promote()` и `/effort`-подобный авто-триггер — только после того как ручной режим отработал на реальных задачах.
