# Agent Note: Установщик не запускался — fallback-resolution обрезалась на junction'ах

Status: implemented

## Problem

Установленный сборкой exe падал при первом же запуске ярлыка: бут умирал на `ERR_MODULE_NOT_FOUND` примерно по сотне пакетов замыкания (`dsh-client-ui-*`, `dsh-session*`, `dsh-llm*`, …), URL не печатался, порт не открывался, а `dsh-web.ps1` слепо ждал свои 90 секунд — для пользователя это выглядело как «завис в PowerShell». При этом смоук сборки проходил, и dev-запуск из чекаута работал.

## Decision

Причина — `healProfilesModuleFallback` (`dsh-app-boot/src/profile.ts`): BFS по дереву зависимостей шёл от пути **junction'а**, а не от real path пакета. В dev-дереве pnpm поднимает все рабочие пакеты и хвосты в корневой `node_modules`, поэтому обход «видел» всё. В задеплоенном (изолированном) layout транзитивные зависимости лежат в сторе рядом с real-каталогом пакета и с пути junction'а не видны — BFS молча пропускал их (`packageDirFromAnchor` возвращал `undefined`), fallback наполнялся лишь прямыми deps якоря, и почти всё замыкание переставало резолвиться из профиля.

Исправление — `realpathSync` найденного каталога перед обходом и перед записью в links (с одновременной защитой от Windows-префикса `\\?\`), плюс JSDoc-контракт. Скрытность отказа (молчаливый skip) сохранена по исходному контракту «declared-but-uninstalled», но теперь skip срабатывает только там, где пакета действительно нет.

Смоук сборки переведён на **чистый `DSH_HOME`** (`scripts/build-windows-installer.ts`): временный пустой домен заставляет staged-бут хилить fallback исключительно из стейджинга — именно тот сценарий, что ломался. Раньше смоук незаметно ездил на dev-вылеченном `~/.dsh/profiles/node_modules` и этот класс багов не ловил в принципе. Заодно смоук уже отключал трей (`DSH_WEB_TRAY=0`). Попутно, из того же отчёта о «зависании»: лаунчер `dsh-web.ps1` получил живой прогресс ожидания, дедлайн 240 с вместо слепых 90, немедленный провал с хвостом лога при смерти процесса и явное сообщение, когда процесс жив, но порт ещё не открыт.

Регрессия — тест «walks realpaths so an isolated store layout links junction-hidden transitives»: изолированный layout с junction'ом на стор, транзитив виден только через real path; на старом коде тест падает (проверено stash-пробой), на новом зелёный.

## Alternatives considered

- Полная расплющенная установка (hoist всех пакетов в корень deploy) — отклонено: меняет семантику деплоя всего продукта ради одного потребителя, а изолированный layout остаётся корректным носителем.
- Резолвить имена прямо из `.pnpm`-стора по соглашению — отклонено: приватная деталь pnpm, контракт же — «Node's own lookup order from the real directory».
- Оставить как есть и требовать, чтобы install всегда шёл после dev-запуска на той же машине, — отклонено: это и есть баг, просто узаконенный.

## Consequences

Установленное приложение больше не зависит ни от dev-чекаута, ни от предварительно вылеченного `~/.dsh/profiles/node_modules`: первый же запуск хилит fallback из собственного дерева. Dev и установленный экземпляры по-прежнему делят один fallback и при чередовании запусков перетирают ссылки друг друга (существующее поведение «moved installations are re-pointed») — запуск приложения на другой установке просто пере-пойнтит их за один проход. Смоук теперь ловит регрессии резолва установленного layout'а на каждой сборке; цена — создание и удаление временного домена на прогон (несекундное).
