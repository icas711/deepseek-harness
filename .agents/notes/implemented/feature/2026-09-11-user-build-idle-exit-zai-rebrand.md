# Agent Note: Тюнинг пользовательской сборки — idle-выход веб-поверхности, Z.ai по умолчанию, ребрендинг

Status: implemented

## Problem

Сборка для передачи «знакомому пользователю» (Windows-установщик поверх `dsh web`) имела три пользовательских дефекта, унаследованных от базового апстрим-облика:

1. Закрытие вкладки браузера оставляло процесс `node` жить бесконечно: webserver продолжал слушать, а завершить его можно было только вручную (`dsh-stop.ps1` или диспетчер задач).
2. Видимые пользователю поверхности называли продукт «DeepSeek Harness» — заголовок вкладки, PWA-манифест, приветственное уведомление, путь первого запуска, диалог онбординга, тексты установщика.
3. Маршрут по умолчанию был DeepSeek, а список моделей — вендоренный снимок на момент сборки pi-ai: новые модели провайдера (например, glm-5.3) не появлялись до обновления каталога.

## Decision

**Idle-выход.** `WebServer` публикует `openUpgradeCount` — число открытых upgrade-сокетов; страница браузера держит событийный downlink, пока жива, так что это серверный сигнал присутствия без протокольных изменений. Клеевой плагин `web-app` получает поле конфига `idleExitMs` (по умолчанию 600 000, `0` выключает) и раз в 30 секунд опрашивает счётчик: как только браузер подключался и затем отсутствовал дольше окна, плагин пишет строку в лог и вызывает `ctx.get('appExit')(0)` — ограниченный выход лаунчера (полный dispose дерева, затем exit), а не self-dispose собственного фибера, который отключил бы строку из.Loader'а. Интервал `unref`'нут и снимается диспоузером плагина. Сервер, к которому браузер ни разу не подключался, не выходит никогда: бутовые смоки и headless-пробы остаются живыми.

**Z.ai по умолчанию и живой список моделей.** Композиция базы (`dsh-base`) переключает `agent-default-model` на провайдера `zai`, модель `glm-5.2` (флагман glm-5.3 отсутствует в вендоренном каталоге — его приносит живой список), и добавляет в строку `llm-pi-ai` профиль `zai` со стандартным эндпоинтом `https://api.z.ai/api/paas/v4` (не Coding Plan: ключи подписки работают только на coding-эндпоинтах) и `liveModels: true`. Поиск уже был `zai` — изменений не потребовалось. В `llm-pi-ai` появляется поле профиля `liveModels` (требует `baseURL`, иначе отказ при резолве): маршрут с ним не короткозамыкается на вендоренный каталог ни в probe-пути discovery, ни в `listModels` пикера — эндпоинт опрашивается `GET {baseURL}/models` с Bearer-ключом маршрута, ответ сливается поверх каталога (живые записи впереди, каталог-онли — позади), кэш живёт 5 минут на маршрут, неудача запроса оставляет каталогов ответ, чтобы пикер не пустел. Живая запись, которой нет в каталоге, материализуется в дескриптор из протокола, compat и дефолтов ёмкостей маршрута, так что выбранная в пикере модель сразу диспатчится. Путь первого запуска (`ui-settings-models`) перенацелен с deepseek-строки на z.ai: константы `ONBOARDING_PROVIDER`/`ONBOARDING_SETTINGS_NS`/`ONBOARDING_SETTINGS_PATH` в `store.ts`, компонент переименован в `OnboardingDialog`, идентификатор шага — `zai`; готовность читает ту же связку провайдер/настройки/креденшел, редактор ключа переиспользует карточку провайдера и пишет `ZAI_API_KEY` через `credentials.set`.

**Ребрендинг.** Пользовательские поверхности переименованы в «custom-harness»: `<title>` и PWA-манифест `apps/web`, приветственное уведомление (текст переписан, `WELCOME_NOTICE_VERSION` поднят, чтобы все увидели заново), описание шага онбординга, промпт-секция и описание `DSH_WEB_URL` в `web-app`, описание CLI, персона пресета `cordis`, имя приложения и пути логов установщика (`%LOCALAPPDATA%\custom-harness\logs`). Сознательно оставлены: wire-заголовки и User-Agent `x-deepseek-*`/`deepseek-harness/*` (протокол атрибуции, не UI), `BrandWordmark`/`FishLogo` (геометрический глиф без текста), описание строки повторов («запрос к DeepSeek» — точное имя адаптера, чью политику строка правит), тестовые фикстуры и snapshot скилл-контакта `dsh-badge`. Ключless-лан web-e2e остаётся герметичным: scaffold пинит `agent-default-model` на реплей-маршрут, сидирует хранилище креденшелов `ZAI_API_KEY` (кроме сценария первого запуска) и выключает `liveModels` в своей композиции, чтобы пикер не ходил в настоящий api.z.ai.

## Alternatives considered

**Убивать процесс по таймеру от запуска.** Отклонено: долгая сессия с открытым GUI ничем не отличается от забытой; единственный честный сигнал присутствия — открытые downlink-сокеты, которые сервер и так видит.

**WebSocket-ping на уровне приложения.** Отклонено: дублирует транспортом то, что webserver уже знает как факт (`upgradedSockets`), и добавляет собственный протокол присутствия туда, где достаточно геттера.

**Перезаписывать настройки существующих пользователей.** Отклонено: секция `llm-pi-ai:` в `settings.yaml` уже существует у текущих пользователей и перекрывает новую базовую строку целиком по namespace — это контракт слоёного слияния; принудительная миграция нарушила бы «настройки сильнее композиции». Новые установки получают z.ai-профиль из базы.

**Зашить glm-5.3 в каталог.** Отклонено: вендоренный каталог pi-ai — снимок; добавление туда модели, которой нет в установленном pi-ai, ломает резолв полей по умолчанию. Живой список приносит актуальный набор сам.

## Consequences

`dsh web` завершается сам в течение ~10 минут после закрытия последней вкладки (плюс один 30-секундный тик); `idleExitMs: 0` в строке `web` возвращает прежнее поведение. `openUpgradeCount` — публичный геттер `WebServer`, покрывается реальной Loader-композицией (0 → 1 → 0 вокруг upgrade-теста). `listModels` стал асинхронным сетевым путем для `liveModels`-маршрутов: потребители уже `await` его (контракт сшива асинхронен). Пользователи с существующей секцией `llm-pi-ai:` в настройках сохраняют свой профиль DeepSeek и должны добавить маршрут z.ai (или сбросить секцию) вручную, чтобы получить новый дефолт.
