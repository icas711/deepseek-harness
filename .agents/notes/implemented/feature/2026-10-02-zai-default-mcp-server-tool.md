# Agent Note: MCP-инструмент Z.AI как поле профиля маршрута

Status: implemented

## Problem

Эндпоинт Z.AI `chat/completions` умеет серверные MCP-инструменты: в `tools` принимается запись `{"type":"mcp","mcp":{...}}`, эндпоинт сам подключается к MCP-серверу Zhipu и сам исполняет его вызовы внутри одного запроса — клиентского цикла tool-result нет. Harness этой возможностью не пользовался: на Z.AI-маршрутах модель не могла ни поискать в вебе, ни разобрать изображение иначе, как явным инструментом harness с полным кругом вызова. Владелец форка попросил включить MCP для Z.AI-маршрута; после первой реализации (жёстко в коде адаптера по признаку маршрута) владелец перенёс решение в настройки.

## Decision

**Поле профиля.** `PiAiProviderProfile` получает `mcp?: boolean` (по умолчанию выключено). Включённое поле приписывает к каждому запросу маршрута запись официального MCP-сервера Zhipu — `server_label: "mcp code"`, `transport_type: "streamable-http"`, без `server_url` (официальные серверы Zhipu адресуются меткой) и без `allowed_tools` (отсутствие поля документировано как «доступны все инструменты сервера» — без выдуманного списка имён). Форма записи — внешняя спецификация провода — фиксирована в `src/zai-mcp.ts`; настройкой является только её присутствие на маршруте.

**Проверка допустимости.** Поле разрешено только на Z.AI-маршруте — ключ каталога pi-ai (`zai`, `zai-coding-cn`) или эндпоинт на `api.z.ai`/`open.bigmodel.cn`, тот же признак `isZaiRoute`, что решает провижимость, — и отказывает при разрешении профиля с именем маршрута: посторонний OpenAI-совместимый шлюз запись `mcp` не понимает. Признак перенесён из provision-модуля в `catalog.ts`, чтобы `config.ts` мог валидировать поле без цикла импортов.

**Как запись попадает в запрос.** Через документированный хук pi-ai `StreamOptions.onPayload`: pi-ai вызывает его с финальными параметрами запроса перед отправкой, и это единственная точка, где расширение `chat/completions` — тип `mcp`, а не функция с JSON-схемой — попадает на провод без патчей SDK и без подделки типа в `Context.tools`. Функция `withZaiMcpServer` дописывает запись после функциональных инструментов, создавая массив `tools`, если тех нет, и отказывает громко на форме payload, которую не может достроить, чтобы дрейф контракта pi-ai не молча ронял MCP.

**Композиция.** Поставляемый профиль маршрута `zai` в `packages/bundle/base/cordis.patch.yml` ставит `mcp: true`; пользовательский слой `llm-pi-ai:` в `settings.yaml` может переопределить поле по провайдеру.

## Alternatives considered

**Жёстко в коде адаптера по признаку маршрута, без настройки.** Первая реализация: каждый запрос Z.AI-маршрута нёс запись безусловно. Отклонено владельцем форка («просто пропиши в настройках»); этому же соответствует правило проекта — развёртывающий выбор живёт в конфигурации, а не в `DEFAULT_*`-константе адаптера.

**Полный структурированный конфиг MCP-серверов (`server_url`, `allowed_tools`, `headers`, свои серверы).** Отклонено как спекулятивное обобщение: единственный текущий потребитель — официальный `mcp code` на Z.AI-маршрутах; появление стороннего сервера — отдельное решение со своей записью здесь. Список `allowed_tools` тоже не настраивается: документация Z.AI перечисляет инструменты только примерами, и выдумывать набор — изобретать политику без основания.

**Прокинуть MCP-запись через `Context.tools` pi-ai.** Отклонено: тип `Tool` — функция с JSON-схемой; расширение протаскивалось бы подделкой типа через весь контекстный слой, а `onPayload` существует именно для доводки провайдер-специфичных параметров.

**Свой MCP-клиент в harness.** Отклонено: серверное исполнение Z.AI не требует клиентского цикла; локальный клиент добавил бы реестр инструментов, события сессии и таймауты ради того, что эндпоинт уже делает сам.

## Consequences

- Маршрут `zai` из поставляемой композиции умеет то, что умеет официальный MCP-сервер Zhipu (веб-поиск, анализ изображений и видео), без round-trip через инструменты harness; решение об вызове принимает модель.
- Поле по умолчанию выключено: включение — явная настройка маршрута, не-Z.AI маршрут включить его не может (отказ при разрешении профиля с именем маршрута).
- Не-Z.AI шлюз, названный ключом каталога `zai`/`zai-coding-cn` с включённым `mcp`, получит запись, которую может не понять: ключ каталога и есть заявление «это Z.AI».
- Реестр инструментов и журнал сессии MCP-вызовов не видят: модель-видимый вход остаётся функциональными инструментами harness, а исполнение живёт внутри ответа эндпоинта.

## Тестирование

`packages/llm/llm-pi-ai/tests/zai-mcp.spec.ts` — блок `withZaiMcpServer` (дописывание после функциональных инструментов, создание массива, отказ на чужой форме payload), отказ `mcp` на не-Z.AI маршруте при разрешении профиля, и реальная композиция через mock-сервер: маршрут `zai` с `mcp: true` несёт запись в уходящем теле запроса с инструментами harness и без, без поля — не несёт.
