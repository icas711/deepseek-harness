# Agent Note: Telegram-уведомления о задачах оркестратора

Status: implemented

## Problem

Супервизор задач (`ctx.taskSupervisor`) ведёт durable-реестр, но человек узнаёт о состоянии задач, только открыв веб-интерфейс: задача, приостановленная рестартом или проваленная ночью, ждёт, пока пользователь сам посмотрит. Нужен канал «сервер → человек» вне браузера. У шва два неудобных свойства: адресат — человек за логином, а не модель, и транспорт — внешний сервис, который у части развёртываний отключён вовсе.

## Decision

Новая группа `packages/notify` делит возможность на шов и провайдера. Service Definition `@deepseek-ai/dsh-notifier` (сервис `ctx.notifier`) не знает про Telegram: `send({ login, kind, title, sessionId })` доставляет уведомление в пункт доставки, привязанный к логину (незавёршенный логин — тихий пропуск, неудача доставки — исключение), `beginBinding(login)` выдаёт одноразовый код с ограниченным сроком, а базовый класс владеет durable-документом биндингов `telegram-bindings.json` (слияние под writer-lock, `0600`) и таблицей ожидающих кодов в памяти. Провайдер `@deepseek-ai/dsh-telegram-notifier` — Telegram Bot API обычным fetch: `sendMessage` для доставки, периодический короткий `getUpdates` (без webhook и входящих портов) для приёма `/start КОД`; тексты бота — русские константы, закреплённые снапшотом. Пустой `DSH_TELEGRAM_BOT_TOKEN` — пассивный режим строки по образцу `web-auth`: сервиса нет, таймеров и сети нет.

Consumer живёт в провайдере: у супервизора нет ленты событий, поэтому наблюдатель раз в `watchIntervalMs` (валидируемое поле, минимум 50 мс) читает `list()` и сравнивает статусы с прошлым опросом в памяти. Переход в `paused`/`interrupted` — «Требуется действие», `completed`/`failed` — свои заголовки; в тексте только название задачи, статус и ссылка `DSH_WEB_URL` + `/session/` + `sessionId`. Дедупликация — одно активное уведомление на пару (задача, статус): пара переоткрывается, когда задача уходит из статуса; пара без доставки (сбой транспорта или ещё нет биндинга) остаётся неотмеченной и повторяется. Уведомления адресуются всем логинам с биндингом (`boundLogins()`).

Проводка: строка `telegram-notifier` в `packages/bundle/web-app/cordis.patch.yml` (определение шва монтируемой строки не имеет — это библиотека абстрактного сервиса, попадает в сборку зависимостью провайдера), абзац в README бандла, обе зависимости в `package.json` бандла, агрегаты `tsconfig.host.json` и таблица `packages/README.md`.

## Alternatives considered

**Добавить ленту событий в `dsh-task-supervisor`.** Отклонено в рамках этапа: пакет готов и рекомендованным путём назван внешний дифф по `(taskId,status)`; лента событий — расширение контракта супервизора, которое нужно сначала спроектировать (гарантии доставки, backpressure), а не прикреплять к потребителю-уведомителю.

**Telegram webhook вместо `getUpdates`.** Отклонено: webhook требует входящего порта и публичного HTTPS-адреса — развёртывание за NAT или обратным прокси без терминации теряет уведомления; короткий опрос работает везде, где работает сам сервер.

**Адресовать уведомление владельцу сессии.** Отклонено на этом этапе: реестр задач не хранит логин владельца, и выводить его некорректно ни из чего; наблюдатель рассылает всем привязанным — при появлении владельца в реестре или через RPC адресация станет персональной.

**Хранить ожидающие коды в durable-документе.** Отклонено: код — короткоживущий одноразовый факт сессии сопряжения; рестарт, обнуляющий коды, безобиден (пользователь запрашивает новый), а отдельная таблица в файле добавила бы ещё один формат и чистку протухших записей.

## Consequences

Уведомления работают end-to-end под REAL-композицией через Loader (биндинг по коду → `markFailed` → сообщение в подменённом транспорте), дедуп и дифф статусов покрыты юнит-сьютом, тексты закреплены снапшотами. Цена: коды сопряжения живут только в памяти процесса; выдача кодов пока доступна только как API сервиса — страницы «Уведомления» и RPC на следующем этапе; уведомления уходят всем привязанным, а не владельцу сессии; отвязки логина нет (ограничение документа биндингов). `getUpdates` с offset 0 забирает непрочитанные обновления лишь за сутки — более старый код не сработает.
