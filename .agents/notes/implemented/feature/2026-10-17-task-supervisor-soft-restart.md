# Agent Note: durable-супервизор задач с мягким рестартом

Status: implemented

## Problem

Долгая задача веб-сессии живёт не дольше процесса: рестарт сервера (обновление, сбой) теряет факт работы — сессия остаётся холодной, и никто не продолжает её. Нужен durable-факт «на сессии есть незавершённая задача» и механика мягкого рестарта: чистая остановка должна парковать работу, следующий старт — продолжать её сам, а сессии, на которых процесс упал, — помечать отдельно. Текста продолжения модель видит только через обычный вход в лог: новых типов событий вводить нельзя.

## Decision

Новый пакет `@deepseek-ai/dsh-task-supervisor` (сервис `ctx.taskSupervisor`, группа `host`) владеет реестром `dshHomePath('task-registry.json')`: записи `{ taskId — брендированный opaque id, sessionId, title, status: running|paused|interrupted|completed|failed, updatedAt }`, каждая мутация — цельный документ через writer-lock и атомарную замену `dsh-atomic-write`. API: `track` (идемпотентен по `sessionId`), `markCompleted`, `markFailed(taskId, reason)` (причина — в логе процесса), `list`, `resume(taskId)`.

При выгрузке fiber'а супервизор сначала гасит незавершённые возобновления, затем одной записью переводит все `running` в `paused` до прочей разборки и только потом dispose'ит поднятых им агентов. При старте `running`-записи означают жёсткий сбой предшественника: одной записью они становятся `interrupted` и автоматически не возобновляются; `paused`-записи возобновляются сами по `ctx.inject(['agentLoop'])` — холодная сессия открывается по образцу resume-политики api-proxy (живой агент переиспользуется, пресет сессии собирается из лога), и в инбокс ставится обычное пользовательское сообщение с константой «Задача была прервана рестартом сервера. Продолжи выполнение с места остановки; сначала кратко восстанови контекст по истории.» (константа закреплена снапшот-тестом).

Проводка: одна строка в `packages/bundle/web-app/cordis.patch.yml` (ряд `task-supervisor` с `registryPath: dshHomePath('task-registry.json')`), абзац в README бандла, ссылка в `packages/host/README.md` и `tsconfig.host.json`. При пустом реестре строка пассивна.

## Alternatives considered

**Хранить состояние задач в session-log новым типом события.** Отклонено: задача — факт над сессией и процессом, а не событие её истории; реестр должен читаться до открытия сессии, а правило «модель-видимое ⟺ записано» здесь не нарушается — продолжение доставляется обычным `user/message`.

**Возобновлять `interrupted` автоматически вместе с `paused`.** Отклонено: жёсткий сбой может оставить неконсистентное окружение (полу-применённые правки, подвисшие процессы); решение о продолжении после сбоя — за владельцем задачи через явный `resume`.

**Расширить `dsh-jobs`.** Отклонено: `jobs` — процесс-локальный реестр фоновых операций с dispatch-контрактом и собственным набором статусов; здесь нужен durable-факт между процессами, и смешение ролей сломало бы оба контракта.

**Ретрай `EPERM`-переименования внутри `dsh-atomic-write`.** Отклонено в рамках границ этапа: общая утилита держит зафиксированный контракт (replace — одна попытка, contention — у writer-lock); окно рестарта со сканером на свежем файле — сценарий самого супервизора, поэтому ограниченный бэкофф замены живёт в его реестре.

## Consequences

Мягкий рестарт перестал терять работу: парковка/возобновление покрыты REAL-композицией через Loader (boot → track → dispose → boot → продолжение у мок-модели), жёсткий сбой — отдельным тестом (`interrupted` без возобновления). Цена: в композиции по умолчанию API сервиса никто не вызывает — модель-видимого управления задачами (инструмент/RPC) и статуса `waiting-human` нет, это Known Limitations этапа; авто-возобновление требует в композиции persistence и agent-loop; выбор модели сессии при холодном открытии не восстанавливается (берётся дефолт `ctx.agentDefaultModel`). Реестр только растёт: чистки завершённых записей нет.
