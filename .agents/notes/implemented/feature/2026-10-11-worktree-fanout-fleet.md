# Agent Note: Оркестрация worktree-фанлаута — флот параллельных сессий

Status: implemented

## Problem

dsh работает как сервер на облачной машине, а пользователь управляет сессиями из браузера локального компьютера и телефона. Для задач с высокой неопределённостью нужен паттерн «один промпт → N параллельных попыток в изолированных git worktree → сравнение результатов → слияние победителя» (референс — Orca ADE). Существующие механизмы его не дают:

- Фоновые субагенты ([background subagent tasks](./2026-07-08-background-subagent-tasks.md)) дают параллельность, но транскрипт ребёнка сворачивается в один `job_output`-результат: попытка невидима в Web GUI как сессия, её нельзя наблюдать с телефона и вмешаться в неё.
- [Ralph](./2026-07-19-fresh-agent-ralph-workflow-tool.md) и workflow-движок — фиксированные политики внутри одной композиции с той же проблемой видимости; `workflowEngine` не управляет git-worktree.
- [fork](./2026-06-30-session-store-fork-api.md) создаёт одну сессию-потомка без управления набором попыток, git-изоляции и сравнения.

Пользователю нужно, чтобы каждая попытка была обычной сессией: видимой в существующем списке сессий, сгруппированной под своим workspace, наблюдаемой и управляемой с телефона.

## Decision

Capability-группа `packages/fleet/` из трёх пакетов, по шаблону семейства jobs:

- **`dsh-worktree`** — capability-пакет `ctx.worktrees`: жизненный цикл git worktree (create/list/remove; пути нормализуются к платформенным разделителям) и веточные глаголы флота — diff рабочего дерева против merge-base (изменения трекаемых файлов плюс untracked-листинг строками `(untracked) <path>` в stat, без мутации индекса) и merge ветки с откатом конфликта и классификацией (`merged` / `up-to-date` / `conflict`). Каждый глагол — один ограниченный git-child через [subprocess-seam](../../implemented/architecture/2026-07-26-subprocess-seam.md) с фиксированным GIT_ENV (`NO_COLOR`, `TERM=dumb`, `GIT_PAGER=cat`, `LC_ALL=C`). Definition и локальный git-провайдер живут в одном пакете до появления второго провайдера.
- **`dsh-fleet`** — сервис `ctx.fleet`: `fanout({ repoPath, count, prompt, baseRef? })` создаёт N worktree с ветками `dsh-fleet/<short8>/m<i>` под `<repo>-dsh-fleet/<short8>/`, регистрирует каждый каталог в `ctx.workspaceRegistry`, создаёт членского агента через `ctx.agents.create({ cwd: <worktree>, delegationDepth: владелец+1, agentOptions: agentDefaultModel.currentSelection() })` и доставляет промпт через `agent.followup()`; частичный провал откатывает созданное. `status()` выводит состояние попыток из живых агентов (`starting`/`running`/`idle`/`gone`); `diff()` — диффы попыток; `merge(fanoutId, member)` сливает ветку победителя (работающая попытка отвергается); `cleanup()` останавливает попытки, удаляет worktree и дерегистрирует workspace. Записи фанлаута процесс-локальны. Первый `turn/end` попытки доставляет владельцу одно уведомление (`inject` занятому, иначе `followup`) по паттерну из [`dsh-tool-jobs`](../../../../packages/jobs/tool-jobs/README.md).
- **`dsh-tool-fleet`** — model-facing Consumer: инструменты `fleet_fanout` / `fleet_status` / `fleet_diff` / `fleet_merge` / `fleet_cleanup` с дисциплиной работы в описаниях; `repo_path` резолвится от cwd сессии владельца; `fleet_diff` обрезается до `maxDiffBytes` по UTF-8-границе кодпоинта.

Владение и время жизни: фанлаут принадлежит сессии-инициатору (owner-fence по `SessionId`, как в [job registry](../../implemented/architecture/2026-07-26-job-registry-seam.md)); выгрузка композиции гасит членских агентов. Членские сессии — обычные персистентные сессии с `cwd` в worktree: видны во всех поверхностях (Web GUI, браузер телефона) без нового UI, после перезапуска возобновляются вручную. Вложенный фанлаут ограничен `maxFanoutDepth` (по умолчанию 2) поверх `delegationDepth`; `maxMembers` (по умолчанию 5) ограничивает размер одного фанлаута.

## Alternatives considered

**Self-host Orca serve.** Готовый продукт с нужным UX, но десктоп-центричный, мобильный реле идёт через их облако, и форк не контролирует поведение. Отвергнуто как замена; Orca остаётся референсом механики.

**Расширить subagent-seam фоновым fan-out в worktree.** Минимум новых пакетов, но цель противоположна семейству: субагент — делегация модели, возвращающая один результат, а не пользовательская сессия. Превращение субагента в top-level видимую сессию сломало бы контракт сворачивания транскрипта.

**Реализовать как фиксированный workflow (как ralph).** Движок workflow не порождает пользовательских сессий и не управляет git; повторяет проблему видимости. Дисциплина ralph (свежий агент на раунд) пересекается, но решает другую задачу — итеративное уточнение, не параллельные попытки.

**UI-first: панель фанлаута в Web GUI вместо инструментов.** Не даёт phone-first сценария через чат («запусти 3 попытки и сравни»), требует нового RPC-слоя до появления какой-либо ценности и хуже покрывается snapshot-тестами. Отложено как следующий шаг поверх той же службы.

## Consequences

- Каждая попытка — полноценная пользовательская сессия в существующих поверхностях; платой служит процесс-локальность записей фанлаута: после перезапуска host worktree, workspace и персистентные сессии остаются, но связь «фанлаут → попытки» теряется (долговечное состояние в storage domain отложено).
- Уведомление владельцу — только о первом `turn/end` попытки; последующие ходы в членской сессии владельца не будят.
- Конфликт слияния не перебирается автоматически: `merge` откатывает конфликт и возвращает классификацию — разрешение остаётся за моделью/пользователем.
- Merge работает по коммитам ветки; незафиксированная работа попытки видна в `diff`, но не сливается.
- Пресет членского агента не выбирается: маршрут членов фиксирован на `agentDefaultModel.currentSelection()`, параметр `agentPreset` отложен до ростера пресетов.
- Windows-специфика git закрыта нормализацией разделителей в `list`/`create` и фиксированным GIT_ENV; кроссплатформенность пиннится тестами с реальным git.

## Testing

- Unit/REAL-composition тесты в `packages/fleet/{worktree,fleet,tool-fleet}/tests/`: жизненный цикл worktree над реальным git во временных репозиториях, полный членский цикл через настоящий agent-loop с mock-адаптером (попытка пишет файл инструментом в свой worktree), owner-fence, композиция через Loader по cordis.yml.
- Keyless snapshot `examples/headless-agent/tests/fleet.snapshot.ts` прогоняет собранное headless-приложение по полному циклу `fleet_fanout → fleet_status → fleet_diff → fleet_merge → fleet_cleanup` c уведомлением о завершении: replay-скрипты родителя и члена, детерминированный git-коммит (фиксированные даты), fence-фикстура пинит момент уведомления, нормализация `{{cwd}}-dsh-fleet/{{fanoutShort}}/m<i>` в золотых файлах.
