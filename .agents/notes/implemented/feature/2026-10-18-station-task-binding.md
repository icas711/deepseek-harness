# Agent Note: Привязка задач к станциям — офлайн-ожидание и автопродолжение (этап 5b)

Status: implemented

## Проблема

Мост станций (этап 5a) давал сервис `ctx.stations` и провайдеры fs-station/subprocess-station, но ни одна сессия не исполнялась на станции: выбор станции для сессии не был подключён, а уход станции в офлайн означал просто поток ошибок шва в текущих ходах. Задача супервизора (`ctx.taskSupervisor`) знала только статусы `running`/`paused`/`interrupted`/`completed`/`failed` — «ждёт машину пользователя» выразить было нечем, и после возврата станции никто не продолжал работу.

## Решение

**Событие смены онлайн-статуса.** `dsh-stations` объявляет типизированное событие `station/status` (`{ stationId, online }`, declaration merging в `Events`). Подъём — только на настоящей смене статуса: подключение после приветствия (`markOnline` при пустой карте) и закрытие живого сокета (`markOffline` под гвардом замещения); замена одного живого соединения другим статус не меняет и события не поднимает (новая сессия ставится в карту до `handleClose` прежней, чей гвард видит живую замену). Подписчики — супервизор и (через дифф реестра) вотчер уведомлений.

**Реестр задач.** Запись получает необязательное `stationId` (бренд из `dsh-station-protocol`), статусный словарь пополняется `waiting-station`. Структурная версия документа не менялась: поле опционально, разбор принимает документ без него, а при наличии требует непустую строку — мусор валит загрузку громко, как любое нарушение границы; старый читатель новый документ отвергнет так же громко на неизвестном статусе. Переходы: `running → waiting-station` (уход станции) и `waiting-station → running/completed/failed`; парковка выгрузки (`running → paused`) `waiting-station` не трогает — уход станции переживает рестарт хоста. `track({ sessionId, title, stationId? })` привязывает и перепривязывает задачу; владение станцией проверяет вызывающая сторона (RPC-граница), сервис доверяет брендированному идентификатору.

**Супервизор.** При `init` (если мост смонтирован) подписывается на `station/status`: офлайн — одной атомарной записью переводит `running`-задачи этой станции в `waiting-station`; онлайн — возобновляет их по механике `paused → resume`. Ход агента при уходе станции не гасится — инструменты офлайн-станции отвечают понятными ошибками шва. Отсюда два правила продолжения: если ход всё ещё в полёте (`agent.status === 'running'`), сообщение-продолжение НЕ доставляется — задача продолжает текущий шаг сама, а followup встал бы очередью за живым ходом; в остальных случаях (холодное открытие после рестарта, простой агент) доставляется обычное пользовательское сообщение со станционной константой «Связь со станцией восстановлена…» — не рестартовой формулировкой. Холодное открытие переприменяет мир станции: провайдеры fs-station/subprocess-station монтируются в скоуп агента с приватными `isolate`-метками; без моста в композиции возобновление привязанной задачи падает громко (`resume-unavailable`) — молча уводить инструменты на локальную машину нельзя.

**Шлюз.** `session.create` принимает `executionTarget: { stationId }`: валидация на wire-границе (станция сопряжена — `station-not-found`; принадлежит логину вызывающего веб-пользователя, админы включительно — `station-forbidden`; нет моста или веб-личности — `stations-unavailable`), затем setup агента монтирует мир станции в скоупе. Привязка — композиция времени создания: на заголовке сессии не хранится; возобновлённая сессия переприменяет мир из привязки задачи в реестре супервизора. Вотчер Telegram дополняется kind-ами `waiting-station` («Задача ждёт станцию» — пользователь должен знать, почему задача встала) и переходом `waiting-station → running` («Станция вернулась — задача продолжена»), один раз на переход; дифф-переходы короче интервала опроса наблюдатель не видит — это свойство любого poll-диффа.

## Альтернативы

- **Хранить привязку в заголовке сессии** (как `agentPreset`) и восстанавливать мир из него. Отклонено на этом этапе: `SessionHeader` — закрытый интерфейс ядра `dsh-session` с валидацией на границе носителя, правки ядра вне границ этапа; привязка задачи в реестре супервизора даёт тот же durable-источник для пути «задача → станция», который и есть предмет этапа.
- **Монтировать провайдеры без `isolate`, в глобальный слот.** Отклонено: `ctx.provide` бросает на второй регистрации того же имени — две станции в разных сессиях исключали бы друг друга; приватные метки — ровно механика preset/isolate.
- **Слать уведомления из супервизора напрямую.** Отклонено: формулировки и адресация — забота провайдера уведомлений (символьная граница notifier); супервизор меняет статусы, вотчер диффом превращает их в доставки. Единый путь дедупликации и ретраев сохраняется.
- **Поднять версию реестра до 2 с обязательным `stationId`.** Отклонено: поле опционально по смыслу (задачи в мире хоста существуют), обязательность вынудила бы переписывать живые реестры без поведенческой необходимости; громкий отказ на мусоре обеспечен валидацией поля и статусного словаря.

## Последствия

Сессия, созданная через `session.create` с `executionTarget`, но без привязанной задачи в реестре, после рестарта возобновляется шлюзом в локальном мире — привязку сессии к задаче делает интеграция владельца задач (следующий этап). Инструменты видят станционный мир только из своего скоупа: хостовые потребители инструментов продолжают исполняться локально, сессионная смена мира наступает вместе с потребителями, смонтированными в том же скоупе (как в пресетах). Двухстрочный монтирующий кусок продублирован в `dsh-task-supervisor` и `dsh-host-apiproxy`: вынос в `dsh-stations` сделал бы пакеты провайдеров зависимыми от моста, который зависит от них.
