# Agent Note: Мост станций — исполнение задач на машине пользователя (этап 5a)

Status: implemented

## Problem

Оркестратор в облаке исполняет задачи агентов, но часть работы обязана идти на машине пользователя: её файлы, её инструменты, её окружение. Пробрасывать порты и давать машине публичный адрес нельзя — она за NAT. Локальные провайдеры `ctx.fs`/`ctx.subprocess` исполняют мир на хосте, а e2b-адаптеры — в облачной песочнице; neither достигает машины пользователя, и простая «удалённая папка» не даёт процессам, stdio и liveness без форка каждого потребителя швов.

## Decision

Мост станций: машина пользователя сопрягается как «станция» через маленький Node-коннектор (`dsh-station pair` / `dsh-station run`), который сам dial-out'ится по WSS к оркестратору на путь `/station-ws`. Три новых пакета и два провайдера делят работу так:

- `@deepseek-ai/dsh-station-protocol` — общая библиотека обеих сторон: версия протокола, закрытые юнионы кадров hello/welcome/reject/req/res/evt с корреляцией по id, полный структурный декодер проводной границы и общая изоляция путей (`resolveWithinRoot` + `realpathWithinRoot`).
- `@deepseek-ai/dsh-stations` — хост-сторона: сервис `ctx.stations` (`beginPairing`/`completePairing`/`list`/`verifyStationToken`/`bridge`), реестр `dshHomePath('station-registry.json')` через dsh-atomic-write со writer-lock и слиянием, upgrade-маршрут `/station-ws` и серверная сессия протокола. Пассивен без пар.
- `@deepseek-ai/dsh-station-connector` — станция: CLI (config.json 0600 в `~/.dsh-station`), переподключение с бэкоффом (1 с → 30 с, ±20% джиттера), исполнитель fs через node:fs и процессов через node:child_process с завершением дерева при разрыве/останове.
- `@deepseek-ai/dsh-fs-station` и `@deepseek-ai/dsh-subprocess-station` — те же швы `ctx.fs`/`ctx.subprocess`, что у локального и e2b-миров: bash/терминальные потребители не форкаются. Полная сессионная привязка провайдеров (preset/isolate) — этап 5b; в 5a они регистрируются конфигом `stationId` и покрыты юнит-доказательством машрутизации.

## Решения дизайна

- **Аутентификация апгрейда — в auth-месте webserver'а.** Владелец места (`web-auth`) получил отдельную ветку: путь `/station-ws` пускается по `Authorization: Bearer <токен станции>` через `ctx.stations.verifyStationToken` (timing-safe сверка sha256), остальные пути — по-прежнему cookie/Basic. Единого владельца допуска не стало два: авторитетная проверка живёт в приветствии протокола (она же связывает сокет со станцией), seat — транспортный фильтр перед маршрутом; без auth-места (локальная композиция) токен проверяет сама сессия.
- **Изоляция путей — двоится.** Хост проверяет корень реестра лексически до отправки (защита от ошибок и быстрые отказы), коннектор повторяет проверку лексикой и realpath самого глубокого существующего предка перед исполнением — его корень и есть реальность; символьная ссылка внутри корня, ведущая наружу, отвергается. Реестр хранит платформу станции: правила разбора путей принадлежат ей, а не хосту.
- **Реестр — merge-on-write.** Тот же шаблон, что у task-supervisor: память ведёт, документ перерисовывается целиком под writer-lock и сливается по `stationId`, битый документ валит загрузку громко. Хост хранит только sha256 токена; полный токен едет коннектору ровно один раз — в welcome-кадре ответа на сопряжение.
- **Проводной формат — JSON поверх WSS-текстовых кадров** с полной структурной проверкой на приёме: нарушивший формат отправитель отключается. Корреляция запрос/ответ по UUID, события процессов — без ответа; порядок stdout → exit гарантирует close-семантика коннектора.
- **Окружение ребёнка собирает хост** (`scrubbedParentEnv` + явные записи спеки) и шлёт по проводу целиком: скраб один, на harness-стороне, коннектор не смешивает своё окружение.

## Alternatives considered

- **Проверять токен только в auth-месте** (без приветствия) — отклонено: тогда seat обязан знать про сессии, а без auth-места мост вообще не аутентифицируется; связку «сокет → станция» всё равно делает только приветствие.
- **Проверять токен только в приветствии** (seat пропускает путь всегда) — отклонено: путь станции стал бы исключением из «обойти seat нельзя», а uniform-допуск вебсервера потерял бы смысл; двойная сверка одного ключа дешевле, чем дыра в составе.
- **SSH-туннель/обратный прокси вместо dial-out WSS** — отклонено: требует на машине пользователя ключи и сетевую настройку; dial-out работает за NAT без единого входящего порта.
- **Реализовать PTY через мост в 5a** — отложено: нативная node-pty на машине пользователя тянет сборку и установщики (этап 6); `spawnTerminal` падает с явной ошибкой, обычный bash через collect/pipe работает.

## Consequences

Сессия с таким миром получает файлы и процессы машины пользователя без форков потребителей; офлайн-станция даёт понятные отказы (`offline`/`FS_IO_ERROR`), а не зависания. Дано взаймы: один живой мост на станцию (свежее соединение заменяет прежнее), события вывода без backpressure (лимиты применяет хост), окна collect без spill-файлов (честный `lossy`), `inherit`-потоки уходят в консоль станции. RPC-домен `station.*` шлюза — минимальная грань для UI этапа 6; офлайн-очередь задач и привязка провайдеров к сессиям — этап 5b.

## Testing

Юнит-тесты: декодер кадров и изоляция путей (обе платформенные ветки, обход через символьную ссылку), разбор реестра и слияние, одноразовые коды и timing-safe токены, сессия хоста на подменённом сокете, бэкофф, исполнитель (fs-версии, escape-отказы, stdout → exit, kill/dispose). Интеграция в одном процессе: настоящий веб-сервер + `StationsService` + настоящий коннектор через реальный WebSocket — сопряжение → fs → spawn → результат → разрыв → переподключение; REAL-composition web-auth: маршрут станции пускается токеном и не пускает без него.
