# Agent Note: Вход по логину-паролю и изоляция кабинетов веб-GUI

Status: implemented

## Problem

Форк разворачивают на арендованном сервере (deploy/, Docker) несколькими людьми. Единственной аутентификацией веб-GUI был общий токен `--token` / `DSH_WEB_TOKEN`: один секрет на всех, вход через `/?token=...`, никакой изоляции — каждый, кто вошёл, видит все сессии и весь workspace. Требование владельца: вход по логину и паролю, у каждого логина свой «кабинет» (своя папка и свои сессии), выделенные админы видят всё; полный отказ от режима токена (проект до релиза, совместимость не обещана).

## Decision

**Аутентификация живёт в вебсервере как место (`registerAuth`), владелец — плагин `web-auth` бандла web-app.** Токен-гейт из `dsh-host-webserver` удалён вместе с флагом `--token`; webserver знает только HTTP-носитель: шлюз аутентификации вызывается до роутов/фолбэка/апгрейдов, отказ владелец пишет сам. `packages/bundle/web-app/src/webauth.ts` — единственный владелец входа: русская страница `/login` без JS (CSP `default-src 'none'`), POST-`/logout`, HTTP Basic для curl, `DSH_WEB_USERS` (`логин:scrypt-хэш` через запятую; генератор `deploy/hash-password.mjs`), `DSH_WEB_ADMINS`. Пустой `DSH_WEB_USERS` — пассивный режим (локальный запуск без гейта); битая запись падает громко на старте. Пароли сравниваются по SHA-256-дайджестам через `timingSafeEqual` — равная длина гарантирована, сравнение не утекает ни длину, ни содержимое; строка готовности и `DSH_WEB_URL` секретов не несут (model-visible ⟺ logged). Полномочия методов не ослаблены: гейт открывает транспорт, loopback-pinned RPC и trusted-host fence в `client-connection` работают как раньше.

**Сессии серверные, одна на логин, 30 дней.** Cookie `dsh_web_session` несёт только случайный id; записи живут в `$DSH_HOME/web-sessions.json` (том, переживает рестарт; атомарная запись tmp+rename; битый файл — громкий отказ с подсказкой удалить). Новый вход под логином удаляет его прежнюю запись; в записи — ревизия хэша пароля (`sha256` строки хэша), смена хэша убивает сессии логина, удаление логина — навсегда. Подбор: 5 неудач подряд с одного адреса → минутная пауза (429 + `Retry-After`), Basic-неудачи считаются в тот же счётчик; неизвестный логин проходит фиктивный scrypt, чтобы тайминги не перечисляли пользователей. Неаутентифицированная навигация (`Sec-Fetch-Dest: document` / `Accept: text/html`) — 302 на `/login`, прочее — 401 с телом `unauthorized`: именно его признаёт single-instance проба `web-startup`, проба не менялась.

**Изоляция выводится из cwd сессии, а не из нового поля владения.** Сессия принадлежит логину, когда канонический cwd её заголовка лежит под корнем кабинета `realpath(workspaceRoot/<логин>)`. Никаких изменений формата логов и wire-протокола. Личность течёт от Cookie-заголовка: fetch-хендлер apiproxy выполняет каждый проход под `AsyncLocalStorage` заголовков (`dsh-host-apiproxy/web-identity`), точки входа читают опциональный сервис `webAuth` (`identityFromCookie`). Не-веб вызовы (TUI, headless, in-process) личности не несут — ограничение не включается; админ (из `DSH_WEB_ADMINS`) видит всё.

Ограничиваются: `session.list`/`session.search` (одна общая граница видимости `listVisibleSessionSummaries`), `session.history` (чужая отвечает `session-not-found`, неотличимо от неизвестной), `session.create` (cwd вне кабинета → `session-outside-root`, workspace вне → `workspace-outside-root`, неуказанный cwd = корень кабинета), `workspace.list`/`workspace.create`, browse-выбор каталогов `host.listDirectory`/`host.createDirectory`. Новые коды ошибок добавлены в `RpcErrorDetailsMap` и zod-ветки схемы.

**Кабинет создаётся при первом входе** (mkdir + realpath, кэш по логину) и регистрируется в workspace-реестре раз за жизнь процесса; identity-сервис даёт root шлюзу. Разметка `<meta name="dsh-web-auth" content="on">` в index.html (index-tap вебсервера) включает кнопку «Выйти» в футере боковой панели (`ui-sidebar`, своя кнопка оболочки, слот `sidebar.footer.action` остаётся расширениям; иконка `IconLogoutOutline16` в `ui-primitives`). Истёкшая сессия: fetch-вызовы браузера получают 401 → `redirectToLoginWhenUnauthorized` ведёт на `/login` (`dsh-client-connection`).

## Alternatives considered

- **Гейт внутри `client-connection` (расширение `isTrustedApiRequest`)** — закрывает только `/api`-маршруты и upgrade'ы реестра; статика, fallback-владелец и страница входа остались бы открытыми. Единая точка перед всем диспетчем — webserver (унаследовано у токен-заметки, поглощённой этой).
- **Владелец сессии как поле лога** — меняет формат сессий и требует миграции существующих логов; принадлежность по cwd даёт ту же границу бесплатно, а «старые» сессии в корне workspace естественно становятся админскими.
- **JWT вместо серверных записей** — неотзываемы без инфраструктуры; требование «один логин = одна сессия» и «смена пароля отзывает» хочет серверное состояние.
- **webauth отдельным пакетом** — форк не создаёт новых пакетов без нужды; строка бандла с subpath `./webauth` даёт тот же результат без нового манифеста.

## Consequences

Граница изоляции v1 — перечисление и точки входа (list/search/history/create/workspace/browse); прочие `session.*`-по-id полагаются на непредсказуемость id, push-кадры идут всем браузерам (утечка уровня метаданных). Модель угроз — «любопытный сосед»: агенты всех логинов работают в одном контейнере. Счётчик подбора считается по адресу сокета — за реверс-прокси все клиенты делят один бакет. Сессии, созданные до включения входа, видны только админам. Взамен: полный отказ от токена без миграций, ноль изменений wire-протокола и формата логов, локальный запуск без переменных окружения остаётся открытым сервером.
