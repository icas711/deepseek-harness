# Этап 6: задачи, уведомления и пикер станций в продукте

Дата: 2026-08-12 · Тип: architecture · Статус: implemented

## Контекст

Инфраструктура облачного оркестратора готова (деплой, аккаунты, супервизор задач, notifier, станции), но до этапа 6 у неё не было продуктового лица: супервизор ничего не трекал, у notifier.beginBinding не было вызывающего, у станций не было UI выбора. Этап закрывает сборку.

## Решения и границы

**Проводка супервизора живёт в шлюзе (dsh-host-apiproxy), не в ядре.** Принятый промпт (`session.prompt` после admit) регистрирует задачу, исход turn'а (подписка на `session/event` с `turn/end` в волокне шлюза) завершает её: `completed` → markCompleted, `error` → markFailed (текст из errorChain), отмена и `blocked` оставляют running. Причины: шлюз — единственное место, где знают и веб-личность, и executionTarget создания, и жизненный цикл turn'а; флаг такие знания не получает. Всё fail-soft — задача побочный продукт prompting'а: `stopping` супервизора проглатывается молча, прочие отказы — warn без разрыва turn'а.

**Активная запись не переметывается.** Метка задачи — первый промпт: пока запись активна, повторные промпты не зовут track. Завершённая запись при новом промпте сменяется новой задачей (переиспользование сессии = новая работа). Станционная привязка берётся из факта создания (карта executionTarget в шлюзе), при перезапуске процесса — из записи реестра.

**Изоляция tasks.* строже кабинетной.** Владелец задачи — владелец сессии по cwd; даже админ видит только свои, потому что resume запускает работу в чужом списке. Неизвестный и чужой resume отвечают одинаковым `tasks-task-not-found` — probing чужого списка неотличим от опечатки.

**Станционная привязка едет в session.create, а не применяется потом.** Пикер чипом на hero-экране (по образцу чипа пресетов) держит отложенный выбор; ui-conversation передаёт его в connectWorkspace → sessions.create. Станционная сессия не переиспользует blank: переиспользование молча сбросило бы привязку. Привязка фиксируется созданием — правки после создания нет, и это осознанно (мир исполнения определяет историю сессии).

**Ключ сопряжения notifier.* — веб-личность.** beginBinding/status адресуются логину из cookie (гейт по образцу station.*), код не проходит через произвольные параметры запроса. Подтверждение кода — сторона провайдера (Telegram-команда), UI только показывает код.

**Подтверждение владения холодными задачами** (сессия не прикреплена) берёт cwd из персистенса; пропавшая сессия скрывает запись — владение не доказуемо.

## Что сознательно не сделано

- UI выдачи кода сопряжения станции (station.beginPairing вызывается curl'ом с HTTP Basic; путь описан в deploy/README.md) — страница станций остаётся за кадром этапа.
- Push-уведомления браузера: канал — Telegram, сервис-воркер не вводится.
- Полный мобильный перевёрстка списков/чата/апрува: тач-цели подняты на новых поверхностях (страница задач, раздел уведомлений, чип станции), остальное — существующая вёрстка.
- Установщики коннектора (NSIS/dmg) и автозапуск — Known Limitations пакета коннектора.
